## 1. 배경과 문제

| 구분 | 내용 |
|---|---|
| 상황 | 작성자는 AI 에이전트, 프론트엔드, 사이드 프로젝트를 만들며 배운 것을 Obsidian 볼트(PARA, 비공개 repo `obsidian-vault`)에 쌓고 있다. |
| 문제 1 | 볼트의 지식이 공개 글로 이어지지 않는다. 복사·정리·링크 정리·이미지 처리가 번거롭다. |
| 문제 2 | 한국어로만 쓰면 영어·일본어권 개발자에게 닿지 않는다. 직접 3개 언어로 쓰는 건 1인에게 지속 불가능하다. |
| 문제 3 | 볼트는 "세컨드 브레인"이라 비공개 메모·링크·첨부가 섞여 있다. 공개 과정에서 사적인 내용이 새면 안 된다. |
| 해결 방향 | `publish: true` 한 줄로 발행 → 자동 동기화 → 자동 번역 → 사람 검토(PR) → 배포. |

## 2. 목표 / 비목표

**목표**

| ID | 목표 |
|---|---|
| G-1 | 볼트 노트를 마찰 없이 공개 글로 만든다. (작성자 수동 작업 = 프론트매터 + PR 검토뿐) |
| G-2 | 한 편의 글이 ko/en/ja 세 언어로 같은 URL 구조에 제공된다. |
| G-3 | 비공개 노트·첨부·주석이 절대 공개되지 않는다. (fail closed) |
| G-4 | 각 언어권 검색엔진에서 해당 언어 글이 노출된다. (hreflang·sitemap·canonical) |
| G-5 | 1인이 운영 가능한 비용·시간 안에서 돌아간다. |

**비목표 (이번 범위 아님)**

- 다중 작성자, 게스트 포스트, CMS 관리 화면
- 한국어 외 언어로 원문 작성
- 유료 구독, 광고, 회원 기능
- 볼트 전체의 디지털 가든식 공개 (공개는 노트 단위 opt-in만)
- 실시간 번역(요청 시 번역) — 번역은 빌드 전에 확정된 정적 파일

## 4. 핵심 시나리오

### 4.1 작성자: 작성 → 발행 → 번역 검토 (현행 흐름)

| # | 단계 | 작성자 행동 | 시스템 동작 (현행) |
|---|---|---|---|
| 1 | 작성 | 볼트에서 한국어로 노트 작성 | Obsidian Git이 10분마다 `obsidian-vault`에 push |
| 2 | 발행 표시 | 프론트매터에 `publish: true`, 영어 `slug`, `title`, `description`, `tags` 추가 | — |
| 3 | 동기화 | (대기) | 매일 06:00 KST 또는 수동/`repository_dispatch(vault-updated)`로 워크플로 실행 → `sync`가 `src/content/posts/ko/`로 복사 |
| 4 | 번역 | (대기) | `translate`가 신규·변경 글만 en/ja 번역 |
| 5 | 검토 | PR(`content/auto-publish`)에서 번역 확인·수정 후 merge | 빌드 성공한 경우에만 PR 생성 |
| 6 | 배포 | — | **미구현** (MVP: merge 시 자동 배포) |
| 7 | 비공개 전환 | `publish: true` 제거 | 다음 sync에서 ko 글·이미지 삭제, 이어서 기계 번역본 삭제 |

## 6. 발행·번역 정책

### 6.1 무엇이 공개되는가

| 항목 | 정책 |
|---|---|
| 공개 단위 | 노트 단위 opt-in. `publish: true` + 영어 `slug`가 있는 노트만. 폴더 단위 공개 없음 |
| 링크 | 비공개 노트로의 위키링크는 텍스트만 남김(현행). 비공개 노트 **제목**이 본문 텍스트로 노출된다는 점을 작성자가 인지해야 함 |
| 첨부 | 이미지·PDF만. 같은 이름 파일이 여럿이면 중단(현행) → 폴더 경로로 임베드 |
| 주석 | `%% %%` 안은 공개되지 않음. 짝이 안 맞으면 중단(현행) |
| `draft: true` | 사이트에는 안 보이지만 **공개 저장소에는 커밋됨**(A-3). 비밀 내용은 draft로 숨기지 말고 `publish`를 끈다 (Q-08) |
| 발행 해제 | `publish` 제거 → 다음 실행에서 사이트·저장소 최신본에서 삭제. 단 git 이력에는 남음 |
| 금지 | 볼트 원본 경로·비공개 노트 내용이 CI 로그·PR에 나오면 안 됨(현행 원칙 유지) |

### 6.2 번역 검토 규칙

| 규칙 | 내용 |
|---|---|
| R-1 | 모든 기계 번역은 PR 검토 후 merge. 자동 merge 금지 |
| R-2 | 검토 최소 기준: 제목·설명, 코드 주변 문장, 용어집 준수, 링크 동작 |
| R-3 | 반복되는 오역 용어는 수정과 함께 `glossary.yaml`에 추가 |
| R-4 | 일본어 검토가 어려운 글은 Q-07 결정에 따름 (예: ja만 늦게 merge, 또는 "검토 전" 표시) |
| R-5 | 번역본에는 AI 번역 고지 + 원문 링크 표시 (REQ-23) |

### 6.3 오래된(stale) 번역 처리

| 경우 | 현행 동작 | 정책 |
|---|---|---|
| 기계 번역, 원문 변경 | 다음 실행에서 재번역 → PR | 유지. **PR에서 수정한 내용도 재번역 시 덮어써짐** → 큰 수정은 용어집·원문 수정으로 반영 (Q-05) |
| 손번역(`sourceHash` 없음), 원문 변경 | 아무 변화 없음 (조용히 낡음) | PR에 stale 경고 (REQ-27). 작성자가 손으로 고치거나 파일 삭제 후 재번역 |
| 번역 실패 | 워크플로 전체 실패, PR 없음 | 성공분만 PR, 실패분은 해당 언어 미번역 상태로 두고 스위처가 흐리게 표시 (REQ-26) |
| 원문 삭제 | 기계 번역 삭제, 손번역은 남음 | 손번역도 PR에서 경고 후 작성자가 결정 |
